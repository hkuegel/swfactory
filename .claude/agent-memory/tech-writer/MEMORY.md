# tech-writer memory

Lessons learned across stories. One rule per line, newest last. Keep under 100 lines.

- Copy setup values (origins, ports, scopes, env keys) from the story's Technical design and the ADR, not from memory, before writing README setup steps (story 001).
- Say in the README that `VITE_*` values are public in the bundle, and never show a secret as a `VITE_` example (story 001).
- Name the dev port wherever a Google OAuth origin is listed, and remind that a port change needs a new origin (story 001).
- Say explicitly when a test command never touches external services and needs no client ID, e.g. `npm run test:e2e` with the fake sign-in (story 001).
- Write a known limitation as one README line that names the follow-up story; don't add a separate section for it (story 001).
- Use CHANGELOG "Added" for new capabilities and "Changed" for existing screens whose behaviour changed, e.g. content moved behind sign-in (story 001).
- Write tables and lists by hand in Prettier style; the user runs Prettier afterwards and the tech writer can't run it (story 001).
- Read the story's Implementation notes "Open points" and the Review for doc tasks; they name the README sections that are owed (story 001).
- Before writing, check `docs/` for developer docs besides ADRs and backlog; in story 001 none existed, so only README and CHANGELOG changed (story 001).
- Check the Test report's "Manual check results" before writing setup steps; hak's real setup overrode the design (publishing needs a homepage and privacy URL, so keep "Testing" with test users locally) (story 001).
- Don't write Google Cloud steps as exact menu names; name the console page URL and the field, and say when a label may differ (story 001).
- For dev-only features, say where they are absent (build, preview, deploy) and name the build check that enforces it (story 004).
- Keep Scripts table column widths in sync when a command name gets longer; re-pad the whole table, then check every row with Grep `^\| .{N} \| .{M} \|$` (N, M = column widths) since Prettier can't be run (story 004, 009).
- Describe controls per cell state from the UX Interactions table: a click on a flagged cell does nothing, flags come off by right-click, long-press or F (story 005).
- Document keyboard extras only if the Implementation notes say they were built (Home/End were optional in UX and built in story 005).
- Don't name planned follow-up stories (e.g. best times) in CHANGELOG or README; document only what exists (story 005, reworded in 006).
- Cite the id of the story that built a change in CHANGELOG, even when it was split off from an earlier story (story 006 split from 005).
- Take README feature text from the ACs and the Implementation notes "Built" list; skip Test report probes and review nits, which are not user-facing (story 006).
- Keep CHANGELOG lines user-facing: name the look and the behaviour, not internal terms like "design tokens" or ADR numbers; put those in the README developer note (story 007).
- Point README links only at files that exist: check the ADR path with Glob before linking it (story 007).
- Describe a restyle with no behaviour change as one "Changed" entry with the story id, not one bullet per visual feature (story 007).
- Name a second Playwright project in README Testing with what it re-runs, and say `npm run test:e2e` runs all projects, because `playwright test` runs every project by default (story 008).
- Write a mode or view feature as one README paragraph under the game's own heading, with the reset rule (reload, sign-out) stated once, because hak asked for short prose (story 008).
- Story files run past 400 lines; read the Test report and Review by offset, since the first read is capped and truncates (story 008).
- Check the Test report's verdict against "Fixed after test" in the Implementation notes before writing; the verdict can say FAIL after the defect was fixed (story 009).
- If a request says "mention ADR X if a list of ADRs exists", grep the README for such a list first; the layout names only the `docs/adr/` folder, so skip it and say so (story 009).
- Under a Scripts row for a headed or GPU-only script, say in one sentence that it opens a window, needs a real GPU and is not in `verify` or CI (story 009).
- Use a code block, not a table, for per-app command lists (`-w apps/<name>`): no padding to keep in sync with Prettier; keep tables for short root lists and verify widths with Grep (story 011).
- In a monorepo, take script names and ports from each workspace's `package.json`, `playwright.config.ts` and `dist-check.json`, not from the story text; e.g. `measure:fps` uses its own port 5175 (story 011).
- When docs move into an app README, keep moved game text verbatim, fix only paths and heading levels, and add developer notes from the app's ADR and `dist-check.json` (story 011).
- Don't document `ready` or `draft` stories as features: omit them from the app README story list even if they have a file (story 011, 010).
- When a story adds a dev-only string to `dist-check.json`, add it to the app README's dist-check note too, because that list is copied by hand (story 010).
- Describe a check's failure rule from the script's exit code and floor constants, not from the story text (story 010, measure-fps exits 1 on a missed floor).
- Insert a new CHANGELOG "Added" line above older lines of the same section, newest story first, because the list is kept in that order (story 010).
- Keep the root `docs/backlog/README.md` status column in mind: it can lag the story's status (010 showed "designed" while in-review); report it, don't edit it outside the brief (story 010).
- Document factory process changes (gate order, retro cost table, checklist) in README "Working with the factory" and the check:structure bullets, and in CHANGELOG with the story id, because hak reads them as user-visible (story 012).
- Give the reviewer checklist and other factory files as relative Markdown links only after a Glob confirms the path (story 012).
- Leave CLAUDE.md out of a tech-writer brief when devops is editing it; the README and CHANGELOG are enough for the factory docs (story 012).
- Describe legal rules as the app applies them, with the source and a "check against the law text" note; never call them binding or legally classified (story 013, org instruction).
- When a new app appears, update the root README line that counts the apps ("Today there are N apps"); it is not generated (story 013).
- For a new app README, take the rules and the default values from the story's Context and the ADR, and state the rounding rule in developer notes, not in the user section (story 013).
