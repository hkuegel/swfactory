# 0011 – Factory landing page: an own workspace `landing/`, React rendered to HTML at build time, published at the Pages root

- **Status:** accepted
- **Date:** 2026-11-12
- **Story:** docs/backlog/021-factory-landing-page.md

## Context

Story 021 adds a public page at the site root `https://hkuegel.github.io/swfactory/` that
explains the factory and links to the published apps. Until now `_site/` holds only one
directory per app (ADR 0010), and `check-dist --out` fails on any other top-level entry. The
page has constraints that no app has:

- no sign-in, no app shell; it is not an app and must not be picked up by anything that
  iterates `apps/` (`/new-app`, `/rebuild`, the app discovery of `build-pages`, `check-dist`,
  `check-structure`, the per-app e2e runs);
- it must read as plain text with scripts off (AC2), yet offer an interactive pipeline
  diagram with scripts on;
- the list of app links and a few figures come from the repository at build time, never
  from app names written into code (AC3, AC8, `check-structure` rule 1);
- it reuses the platform's design tokens and token rules (ADR 0004, ADR 0006), and needs one
  entry animation that the token rules so far forbid outside the sign-in spinner.

The choice of where the page lives and how it renders is costly to reverse: the deploy
script, the dist check, the pages test config and the workspace list all depend on it.

## Options considered

### Where the page lives

1. **Part of the platform (`packages/platform/src/landing/`)** – no new workspace, but the
   platform is a source package consumed by apps and is never built; it would need its own
   build entry, and every app's program would type-check page code it never uses.
   Rejected.
2. **An app under `apps/`** – it would get a sign-in-free shell exception, and every
   `apps/*` iteration (new-app reset, rebuild, dist rules, the platform's sign-in specs run
   against every app, publishing at `/swfactory/<name>/`) would have to skip it. Rejected.
3. **A static page generated by a script (template strings in `scripts/`)** – no React,
   but HTML assembled in strings, global CSS instead of CSS Modules, and DOM code for the
   diagram without the factory's component and test patterns; scripts have no unit test
   setup. Rejected.
4. **An own workspace `landing/` at the repo root** (chosen) – a third workspace kind next
   to `packages/*` and `apps/*`: same toolchain (`createAppViteConfig`, Vitest, token rules),
   not matched by any `apps/*` iteration. The name avoids confusion with the deploy output
   `_site/`.

### How it renders

1. **Client-only React (like the apps)** – an empty `<div id="root">` without scripts;
   fails AC2's plain-text fallback. Rejected.
2. **Vanilla HTML and a small enhancement script** – see option 3 above. Rejected.
3. **React rendered to HTML at build time and hydrated** (chosen) – one SSR build of
   `src/entry-server.tsx` (`renderToString`) and the normal client build, both with the same
   `--base`; `build-pages` writes the rendered markup into the client `index.html`, and
   `main.tsx` hydrates it. Scripts off: the full page as HTML. Scripts on: the same tree,
   then the diagram becomes interactive. Spike 2026-11-12 (scratch copy, Vite 8, React 19):
   CSS Module class names are identical in both builds, hydration reports no error, the page
   has no inline script, and the SSR build must get the same `--base` (without it the links
   pointed to `/<app>/`).
4. **A static-site framework (Astro, Next export, vite-plugin-ssr)** – a new dependency for
   one page. Rejected.

### Build-time data (app links, figures)

1. **A JSON manifest written into `_site/`** – published as a stray file. Rejected.
2. **An environment variable set by `build-pages`** – the dev server would show no apps.
   Rejected.
3. **A virtual module `virtual:landing-data`** (chosen), served by a small plugin in
   `landing/vite.config.ts` that calls `loadLandingData(repoRoot)`: apps discovered by the
   same rule as `build-pages` (a directory in `apps/` with a `package.json`, title from its
   `index.html` `<title>`), figures from the backlog index and the `### Cost` tables, the
   "as of" date from the HEAD commit (`git log -1 --format=%cs`). Both builds of one
   `build-pages` run import the same module, so server markup and hydration data agree.

## Decision

- **Workspace** `landing/` (`@swfactory/landing`), added to the root `workspaces`. It
  depends on `react`, `react-dom` and `@swfactory/platform` (tokens, base CSS, Vite config,
  test setup, token rules); no new third-party dependency. Scripts: `dev`, `typecheck`,
  `lint`, `format:check`, `test`; no `build`, `test:e2e` or `check:dist` script (only
  `build-pages` builds it). No `public/` directory: every file it publishes lies in
  `_site/index.html` or `_site/_landing/`.
- **Publishing:** `build-pages` builds the apps as before, then the landing page twice into
  `_site/` with base `/swfactory/` (SSR bundle to `landing/dist/server/`, client with
  `build.assetsDir: '_landing'`, `build.emptyOutDir: false`), and replaces the outlet comment
  `<!--ssr-outlet-->` in `_site/index.html` with `render()`; it fails if the outlet is missing
  or the markup is empty. `_landing` can never be an app name (`new-app` names start with a
  letter).
- **Dist check:** with `--out`, the allowed top-level entries are the checked apps plus the
  **root unit** `index.html` + `_landing/`. The root unit is required; every one of its files
  is scanned for the platform's `forbidden` strings and for the `forbidden` strings of both
  modes (`standard` and `guestOnly`), whatever the mode, because the page has no sign-in;
  no `required` string applies. Its `index.html` must load at least one module script, and
  every entry asset must lie under `<base>_landing/` and exist. Any other entry still fails.
- **Rendering:** the page renders the static form on the server and in the first client
  render (`useSyncExternalStore` server snapshot); after hydration it switches to the
  interactive form unless `prefers-reduced-motion: reduce` matches.
- **Token rules:** `bypassProblems` gets an option naming the stylesheets that may use
  `animation`; the landing page names its one stylesheet with the entry animation. That file
  switches the animation off under reduced motion; its duration is a landing token of at
  most 2 s that is `0s` under reduced motion, and no landing stylesheet contains `infinite`
  (checked in `landing/src/tokens.test.ts`). This is the exception to "only the sign-in
  spinner animates" (ADR 0004).
- **Tests:** the published root page is tested only on the built site (`npm run
test:pages`): the platform's pages spec opens the root and follows every app link; the
  landing's own specs live in `landing/e2e/pages/` and run as a third project of
  `packages/platform/config/playwright.pages.ts`.

## Consequences

- A new app gets its link on the next deploy without any change outside `apps/<name>`; an
  app without `<title>` fails the landing build.
- `_landing` is written in three places (`landing/vite.config.ts`, `scripts/check-dist.mjs`,
  `packages/platform/config/pages.ts`); a mismatch fails loudly (unchecked entry, or a
  "site app" without `index.html`).
- `npm run build:pages` needs git for the "as of" date; without it the derived figures are
  not shown (AC8), the page still builds.
- The figures on a branch build count the working tree; the deployed page states the date of
  the commit it was built from.
- The dev server (`npm run dev -w landing`) renders client-only (`createRoot` when the root is
  empty); only the built site shows the static form, so every landing check runs against
  `_site/`.
- About 70 kB gzip of React for one page; acceptable for a page that is not on any app's path.
- The page has no inline script, so a Content-Security-Policy could be added later without
  code changes.
